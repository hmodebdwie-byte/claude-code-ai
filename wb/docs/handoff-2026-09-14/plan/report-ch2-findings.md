## 2. What we found (root causes, with evidence)

We ran seven parallel reads of the three repositories — the NestJS/Prisma/Redis backend (`apps/api`, `apps/engine`, `apps/settlement-worker`, `apps/npc-worker`, `packages/shared`), the React trading PWA and the React admin app — one per problem area: chart data, chart motion, timer/progress/PnL, engine performance, API and socket performance, legacy NPC, and PWA shell performance. Each read followed a symptom from the pixel back to the code that produces it, and every claim below carries the file and line where we found it. Alongside the reads we ran the real stack in a workbench and measured it: Redis `MONITOR` and per-channel publish captures, a raw socket.io client on `/line-chart`, direct Redis and Postgres inspection of live rounds, a parity capture on desktop (1440x900) and an iPhone 13 profile, a deliberate Redis restart, and round-boundary screenshots on the phone.

Measured baselines in the workbench at idle (no real traders, NPC flow only):

| Channel / stream | Cadence | Payload |
|---|---|---|
| `engine:events:timer` | p90 gap 1001 ms, regular | ~236 B |
| `engine:events:battle.snapshot` | 1/s | ~390 B |
| `risk-terminal.tick` | 1/s | ~1085 B |
| socket.io room `battle_<id>` | ~5 emits/s | mixed |

Read the tags as follows. **[Confirmed]** means we reproduced it — the code path is unambiguous and cited by line, or we observed the behaviour live, or both. **[Hypothesis]** means the mechanism follows from the code but we could not reproduce it here, because it needs production topology, production traffic or a flag we cannot see; each names the check that would settle it. Severity: *critical* = money or availability, *high* = the main cause of a reported symptom, *medium* = a secondary cause or a real cost under load, *low* = correctness or ops debt with no user impact today.

### 2.1 Chart spikes and cross-device drift (client point 1)

One measurement narrows this before any code is read: in the parity capture the desktop browser and the iPhone 13 profile, logged in as the same demo user at the same time, **received identical socket event streams and identical price sequences**. The difference comes from what each client holds and renders — the history it was given, the ticks it saw, its tab's `sessionStorage`, and its own caps.

**[Confirmed · High] `candleBatch` never contains the active round, and the missing history is drawn as a vertical line rather than a gap.** `buildCandleBatchPayload` takes history only from `getLastCompletedBattleIds()` (`line-chart.gateway.ts:639-648`, loop at `:820-836`); the active battle id is fetched at `:823-828` but only echoed as `active_battle_id`. The data exists and is withheld: with battle 80 ACTIVE we read `chart:history:battle_80 ZCARD=192` while the three completed battles served had ended twelve hours earlier at 1.286–1.296 against battle 80 trading near 1.2388, and a later capture returned `active_battle_id=87`, `included=[84,85,86]`, 200 candles all from 86. Because `buildSeriesData` (`NewChart.jsx:189-225`) feeds points with no whitespace and lightweight-charts spaces bars by index, that hole occupies one bar, and the easing loop animates across it from the stale close (`:1273`) to the first live price while `applyDefaultChartZoom` (`:236-255`) fits the scale to 80 bars spanning both regimes — the spike seen after signing in on the phone and after every resume. The client cannot repair it: `requestLineChartBackfill` (`useWebSocket.js:1591-1611`) needs a cursor the server always sends as `battle_cursor: null`.

**[Confirmed · High] A chart's contents are per-device and per-tab by construction.** Each series is the union of the batch that client received, every `candleClosed` since *its own* connect, its own tick candles, and its own tab's `sessionStorage` (`mergePricesWithSessionClosed`, `NewChart.jsx:143-163`, applied at `:1301`, over `persistCandleClosedSession.js:31-62`, plus `recentCandles: prices.slice(-50)` at `ResumeSyncBridge.jsx:119/145/191/206`, re-seeded by `hydrateMatchFromResume.js:88-97`). That union is then cut by two different caps, 200 in the renderer (`NewChart.jsx:29`) and 300 in the store (`lineChartStore.js:5`), and each device drops its own ticks (`useWebSocket.js:1002`, 40 ms floor). Two devices that connected at different moments hold different bars, so the x-range, first visible bar and price-scale fit all differ.

**[Confirmed · High] Round-to-round price continuity has no database fallback, so a Redis restart produces a cliff.** We reproduced it: after restarting Redis, battle 79 ended at 1.28337 and battle 80 spawned at 1.23677. The resolver tries the Redis last price, then the in-process last end price, then the spawn price of 1.23 plus jitter, and nothing consults `battles.endPrice`, which was correct in Postgres throughout. Because consecutive rounds are drawn as adjacent bars, the 0.0466 difference rendered as one vertical drop.

**[Confirmed · Medium, grouped] Three ways the same round looks different on two screens.** The 200-point cap (`MAX_POINTS`, `candle-types.ts:7`) is applied on every close, on archive and on the batch (`line-chart.gateway.ts:505-508`, `:794-797`, `:897-898`), so each 300-second round keeps only its last 200 seconds — `chart:history:completed:80` starts at 13:54:08 for a round that began at 13:52:28 — and because the cap is global across three battles the payload advertises `included_battle_ids: [3 ids]` while carrying one battle's tail. Quiet seconds are stored as flat candles but never sent (`emitFlatCandleForGap`, `:413-446`; `emitToClients=false` at `:198-206`), so live clients have bars only where trades happened while reconnecting clients get one bar per second, and every batch-driven reset re-spaces the earlier bars. Finally each battle switch or reconnect leaves the line-chart room for 60–100 ms (`useWebSocket.js:273-283`, server leaves at `line-chart.gateway.ts:579-581`), and a `candleClosed` emitted in that window is lost and unrecoverable from the batch.

**[Confirmed · Medium] The easing loop writes animation samples into bars that should hold server closes.** The frame loop at `NewChart.jsx:1077` rewrites the current bar every frame, while `candleClosed` handling (`:1404-1470`) only sets the pending target and the server value written once at `:1344` is immediately overwritten. Each bar freezes at whatever the easing reached — on a backgrounded phone, where the loop is paused, at an unconverged value until the next full `setData`.

### 2.2 Volume bars (client point 1)

**[Confirmed · High] The engine's 200 ms coalescer discards each skipped trade's notional instead of accumulating it.** `shouldPublishEnginePriceTick` (`price-tick-coalesce.ts:12-19`) returns false within 200 ms of the previous tick for that battle and the caller simply skips publishing (`trade-executed.handler.ts:276`, `:281-300`), discarding `volumeScale` — the trade's dollar amount (`market-state.service.ts:196/:236`). The API sums only what arrives (`line-chart.gateway.ts:936`, `candle-aggregation.ts:57`) and loses more to a dedupe key of `price:${battleId}:${eventTime}:${price}:${source}` (`redis.subscriber.ts:815-818`); a comment at `:205` puts engine output at roughly 50 snapshots per second at NPC peak, so most ticks are coalesced away under load. So a $100k order can raise a bar less than a later ~$10k order: bar height reflects which trade was first in its 200 ms window, not notional. In the quiet workbench, with trades more than 200 ms apart, we measured no loss — API zset and engine table both summed 67,520 for battle 80 — so it shows only under bursty or NPC-heavy flow.

**[Confirmed · Medium] One histogram mixes two units, with no real/NPC attribution.** Candles rebuilt from the database carry a tick *count* (`line-chart.gateway.ts:669-678` adds 1 per tick, used whenever the Redis archive is missing, `:731-733`) while live and archived candles carry dollar notional. We saw both at once: battles 77–79 had no `chart:history:completed:*` keys and were served with volume 1–3, while `chart:history:completed:80` carried dollar volume summing 67,520 — and since the overlay autoscales (`NewChart.jsx:910`), the larger unit flattens the other to nothing. `UnifiedCandlePayload` (`candle-types.ts:41-52`) also has no real/NPC split, so the bars read as market activity are mostly simulator volume.

**[Hypothesis · Medium] The live bar shows no volume for up to a second, and the histogram rescales as large bars scroll out of view.** `priceUpdate` carries no volume field (`redis.subscriber.ts:878-886`) and the client defaults it to 0 (`chartNormalization.js:17`), while `applyDefaultChartZoom` pins only the price scale, so the overlay keeps autoscaling to the visible 80 bars (`NewChart.jsx:28`, `:236-255`) and once a large bar leaves that window the next largest renders at full height. Running with `ENGINE_PRICE_TICK_COALESCE_MS=0` would separate this from the coalescer loss.

**[Confirmed · Low/Medium] Two candle pipelines exist, only one is shown, and the unshown one is itself racy.** The engine's `CandleProjectionService` records every trade uncoalesced at full notional into Redis and the Postgres `candles` table (`index.ts:216-226`, `:410-427`) and nothing outside `apps/engine` and `packages/shared` consumes it: for battle 80 it held 300 rows summing 124,545 against the API window's 67,520, so admin and database figures disagree with the app chart. Its per-trade update is also an unserialized read-modify-write (`market-state.service.ts:230-233` into `candle-projection.service.ts:82/:95`), so concurrent trades overwrite each other's volume and tick counts.

### 2.3 Time cursor, cooldown motion and round-start motion (client point 2)

The time cursor is a DOM element (`<div class="chart-expiry-line">`) positioned every animation frame by a hand-built map (`seedExpiryMap`, `NewChart.jsx:412-422`; `expiryXFromMap`, `:432-439`): x = pixel of the newest bar + plot offset + `(clamp(progress, 0, 1) + 1) * barSpacing`. Three of those four inputs are wrong or meaningless in the current data model.

**[Confirmed · High] The cursor's bar spacing is a constant 6 px that the chart never uses.** `NewChart.jsx:395-402` reads `chart.timeScale().options()?.barSpacing`, which in lightweight-charts 5.1 returns a clone of the stored *options* — a field only read, never written back by `setBarSpacing`, `setVisibleRange` or pinch-zoom — and the chart is created without a `barSpacing` option (`:846-892`), so it stays at the library default of 6 while real spacing after `applyDefaultChartZoom` is plot width / 80, about 3.9 px on a 390 px phone. The same stale value makes the `spacingChanged` guard (`:1113-1116`) unable to fire, including on pinch-zoom. So the cursor sits 6–12 px right of the newest bar at any zoom and sawtooths: `shiftVisibleRangeOnNewBar: true` keeps that bar's pixel stationary, so the cursor ramps 6 px right over a second and snaps back when the next append re-anchors the map (`:1356-1357`).

**[Confirmed · High] Any full reset with a short series collapses the zoom and throws the newest bar — and the cursor with it — to a quarter of the plot width.** `applyDefaultChartZoom` (`:256-279`) calls `setVisibleRange` over `min(80, rawData.length)` bars, so the library sets `barSpacing = width / length` clamped by `maxBarSpacing = 0.5 * width`, after which `applyOptions({rightOffset: 18})` is clamped by `maxRightOffset = width/barSpacing − min(2, points.length)`. With plot width W:

| Bars in series | Effective rightOffset | x of newest bar |
|---|---|---|
| 1 | 1 | 0.25 W |
| 2–3 | 0 | 0.75 W |
| 10 | 18 | 0.15 W |
| 20 | 18 | 0.075 W |
| 40 | 18 | 0.54 W |
| 80+ | 18 | 0.77 W |

The single-bar case is deterministic at round start: `newBattleStarted` empties `lineChartStore`, the effect re-runs on an empty store (`:1246-1257`), and the engine's synchronous first tick at battle creation (`battle-engine.service.ts:653`) arrives alone so `:1326` resets with n=1 — the `candleBatch` that would restore about 200 bars arrives only after the 80 ms resubscribe gap plus three Prisma queries and a rebuild. It also happens racily at battle end, when a late old-battle candle lands after the store was emptied (`battleEndTransitionService.js:116-121`) and trips `:1329`, while `onBattleEndDetails` re-captures the final snapshot after its own reset and leaves `candles: undefined` (`finalBattleSnapshotService.js:62/:96`), so `Matches.jsx:75-83` cannot re-hydrate and the collapse persists through the cooldown. This is the reported jump far left at battle end and back right at the next match, and the bar-spacing change it carries (about 156 px to 3.9 px) is the "strange motion" of the chart itself.

**[Confirmed · Medium] The x-axis measures trades, not time, so the cooldown has zero width and nothing can move during it.** A bar exists only where the server delivered activity: flat candles are suppressed (`line-chart.gateway.ts:198-206`), the engine publishes no timer-driven ticks (`battle-engine.service.ts:609`), the client drops `priceUpdate` while the cooldown UI is exclusive (`useWebSocket.js:964`), and no whitespace points are inserted. Since x is a function of bar index, the 30-second cooldown occupies 0 px and the cursor is frozen for its duration; the requested "stay where the match ended and move right as time passes" is not expressible on this axis without flat candles or client-side whitespace seconds. Progress is also measured against local `Date.now()` with no server-offset estimation, although `server_time` is in every payload.

**[Confirmed · Medium] Round start performs two to three conflicting re-layouts inside one second.** The first `candleClosed` with a null `lastTimeRef` does `setData([seedPoint])` then a 400 ms `scrollToRealTime()` (`:1420`, `:1439`); the `candleBatch` that follows flips `serverHistoryReady`, re-runs the effect, does `setData(all)` plus `applyDefaultChartZoom`, and the range invalidation cancels that animation mid-flight, after which the zoom switches the price scale to manual (`:277-278`) and the next append switches it back (`:1366`). If `finalBattleSnapshot` is still set when `newBattleStarted` arrives, the effect first paints the previous round's 300 candles (`:1297-1299`) before any of it.

The round-boundary screenshots on the iPhone profile match these findings exactly: at T-1 s the cursor sits just right of the newest bar (the constant 6 px lead); six seconds into the 30-second cooldown the cursor and its "Time left" label are pinned at the far **left** edge, x = 0, the collapsed-zoom state with the label at its unwritten default position; and one second into the next round the previous round's bars are still shown with a one-bar vertical step to the new round's first price, with the cursor back at the right.

**[Hypothesis · Low, grouped] The cursor is unmounted at both boundaries by a field the server never fills, and the loop that moves it is wasteful.** `resolveExpiryReferenceSec` (`:748-772`) depends on `displaySnapshot.end_time`, but the API sends `end_time: battle.endTime` (`battle.service.ts:769/1189/1294`), NULL while a battle is ACTIVE (we confirmed the empty column), so visibility reduces to `cooldownActive || timer.time_remaining != null` and `setTimer(null)` at battle end unmounts an element whose JSX default is `style={{left: 0}}` (`:1531-1537`); on remount the first write is skipped when x is within 0.05 px of `displayExpiryXRef` (`:1124`), which is reset only in the effect at `:1254`, so the element can keep `left: 0`. **[Confirmed · Medium]** Separately the loop re-arms unconditionally (`:1154`) and calls `series.update` every frame, and `syncRoundEntryLabelY` takes two `getBoundingClientRect()` readings per frame (`:352-360`, `:1136-1147`) despite the comment at `:334-337` saying offsets are never measured per frame.

### 2.4 Pool progress bar labels (client point 2)

**[Confirmed · Medium] The labels are children of the width-clamped fills, so the smaller pool's number is overlapped by the indicator dot.** Each amount is rendered inside its own segment (`TradingPanel.jsx:983-1004`) whose width is `clamp(var(--min-pos), var(--sell-percent), var(--max-pos))` with `--min-pos: 13%` and `--max-pos: 87%` (`TradingPanel.jsx:61-62`, `TradingPanel.css:88-89`). At the 13 % floor on a 360–400 px bar the segment is about 47–52 px, and minus 12 px padding that leaves 35–40 px, while a bold 15 px label such as `$3.16K` or `$203.7K` measures 55–65 px; both fills set `overflow: visible` (`:93-119`) and `.progress-label` has no `position` or `z-index` (`:148-157`), so the text overflows into the 22 px white dot positioned at the same clamp with `z-index: 9` (`:159-183`). In the round-boundary screenshots the dot sits on the tail of the smaller pool's label, "$26.96K". `FriendProfileModal` receives the same props (`:1142-1147`) and inherits this wherever it reuses the CSS.

**[Confirmed · Medium] The bar also runs a permanent frame loop that rewrites the clamp every frame.** `TradingPanel.jsx:756-781` reschedules unconditionally and writes `--sell-percent` even when the value equals the target, invalidating both `clamp()` widths and the dot's `left` 60 times a second for a value that changes a few times a second.

### 2.5 Profit estimator delay (client point 2)

**[Confirmed · High] The Market Flip fetch loop invalidates its own in-flight responses on every pot tick, then holds the new verdict for another 1.5 s.** `useMarketFlip.js:52-98` increments `requestIdRef` on every *effect re-run* rather than per dispatch, aborts the previous request (`:65`) and discards any response whose id is stale (`:72`); the effect depends on `potSignature`, both pots rounded to whole dollars (`WinEstimatorSheet.jsx:138-141`), and pots move on essentially every snapshot (server gap 250 ms; battle 81 had buyPot 203,695 against sellPot 3,160). The 250 ms debounce therefore never matures, only the 1500 ms ceiling (`:91-94`) forces a request, and that response is accepted only if it returns before the next pot tick — best case about 2–2.5 s including the 200 ms API coalesce and 50 ms client throttle, and when REST latency exceeds the inter-tick gap *every* response is discarded and the row keeps the previous verdict or "Updating…" indefinitely. A LOSING response that does land is still held for `VERDICT_DAMP_MS = 1500` (`:235-268`). None of this shows in error metrics: the requests succeed and the client drops them.

**[Confirmed · Medium] "Potential payout" uses a different price source and projection than the estimator, and cannot show a loss.** `getTradingDashboardPayload` reads the price from Postgres (`priceTick.findFirst`, `battle.service.ts:2153-2158`) on a table batch-flushed every 150 ms, while `marketFlip` reads Redis `ticktrade:price:last` (`:319-321`), so the panel can read `+$X` while the sheet reads LOSING. A losing user's payout is computed as 0 (`:2367-2400`) and the client colours it from the already-clamped value (`TradingPanel.jsx:936-940`, `:1120-1122`), so the red branch is unreachable and `displayPnlForUI` (`:934`) is never rendered; the only losing signal is `+$0.00`, arriving 1–1.6 s after the snapshot through a 500 ms throttle, a per-user dedupe, a 500 ms coalescer and a 120 ms debounce.

**[Confirmed · Medium] The scenario cards fire a `POST /battle/estimate-payout` on every $1 pot move while the sheet is open.** `useWinEstimate.js:37-74` uses a 200 ms debounce with no ceiling and the same effect-scoped invalidation against the same dollar-granularity signature — two to four posts per second per open sheet under NPC flow, each running the full stake/NPC/`price_ticks` load twice server-side, most then discarded. All three estimator paths, plus the dashboard, the trade stream and the balance snapshot, independently recompute the same `computeLiveProjectedSettlementPayouts`, which loads every `price_tick` row of the round (`battle-payout.live.ts:299-303`), several times per second.

### 2.6 ROUND ENTRY line leaving the screen (client point 3)

**[Confirmed · High] The entry line is a price line, and price lines are never part of autoscale.** `NewChart.jsx:1197-1210` creates it with `series.createPriceLine({ price: entryPrice, … })` while the area series has no `autoscaleInfoProvider` (`:878-896`) and no primitive. In lightweight-charts 5.1 the range comes from the series' visible closes plus series primitives, and custom price lines are consulted only for drawing their own label — so the range is fitted to the bars and the line is drawn wherever that price falls, inside the plot or outside it.

**[Confirmed · High] It stayed visible only because the price scale was in manual mode, and it leaves as soon as autoscale takes over.** Every full reset disables autoscale and sets a manual range padded 16 % around the last 80 bars or fewer (`:277-278`), which early in a round still includes the opening bar near the entry price — hence "it used to stay on screen" — and the first store-path append re-enables autoscale (`:1364-1368`). The window is then 80 bars minus `rightOffset` 18 = **62 bars, about 62 seconds of a 300-second round**, so after roughly a minute the opening bar has scrolled out and any move larger than the visible high-low span pushes the line out of range, while `syncRoundEntryLabelY` hides the label when it is off-plot (`:379`, `:387`) so the disappearance is silent. The 200-point cap from 2.1 compounds it: after a reconnect there are no candles in the round-entry region at all.

### 2.7 Legacy NPC: settings that do not do what they say (client point 4)

Two NPC engines share the `npc-worker` process — the legacy `NpcSimulatorService` (16.8k lines) and the organic engine — routed by `NpcEngineSwitch` on `npc_engine_mode`. The admin UI presents six tabs of settings against them; what is actually wired:

| Admin tab / key group | Keys | Legacy | Organic | Note |
|---|---|---|---|---|
| START/STOP flag | 1 (Redis only) | yes | yes | Missing key means ON |
| Engine mode | `npc_engine_mode` | yes | yes | API reader has no DB fallback |
| NPC Behavior (pace, aggression) | 2 | yes | **no** | Aggression scales sizes and caps, never timing |
| Rotation & Limits | 12 | partial | caps/cooldown only | Window, strategy, min-distinct are legacy-only |
| Volume Distribution | 13 | selection weighting only | **no** | `npc_volume_target_amount_nudge_max` never read |
| Pool Balance | 13 | yes | **no** (own group) | Plan keyed inconsistently across transitions |
| Liquidity heartbeat | 6 (`liquidity_*`) | yes | n/a | **No admin UI**, yet places most NPC trades |
| Organic document | 54 fields | n/a | yes | Two "applies" tags inaccurate |

**[Confirmed · Critical] "NPC OFF" is not durable, and a missing flag means ON.** `isNpcSimulatorDesiredActive` returns true when the Redis value is null or empty (`npc-simulator.redis.ts:70-73`), admin STOP writes only Redis (`admin-npc.service.ts:1214-1218`), the worker's 2 s poll starts the controller whenever the desired state reads true (`npc-worker.command.listener.ts:564-573`), and the engine listener re-persists `'1'` on boot when the key is missing (`npc.command.listener.ts:125-140`). We observed the key empty while the worker was active and the organic engine reported running, with no START ever issued. Any Redis restart, flush or eviction after an admin STOP therefore re-enables NPC trading (which spends `npc_traders.balance` with auto top-up and, in legacy mode, force-wins pots against real users) while the admin page reports RUNNING from the same default.

**[Confirmed · High] The API and the engine can disagree about which engine is running.** `engine-mode.redis.ts:16-34` reads only Redis and returns `'organic'` when the key is missing or on error, while the engine and worker fall back to `system_settings` (`organic-settings.source.ts:100-111`); the key is written only by `AdminNpcOrganicService.persist` and nothing re-mirrors it — we observed it empty against a populated DB value. With DB `legacy` and the key gone the worker runs the legacy simulator while the API believes organic and skips the endgame dominance await (`trades.service.ts:1457-1459`, `:2871-2880`), so a real user's order returns before the legacy counter-trade lands — money-affecting in legacy mode.

**[Confirmed · High] Rotation limits count trades rather than sessions, are advisory under starvation, and are bypassed by three of the five producers.** Participation commits per trade (`npc-simulator.service.ts:15729-15737`, `create-organic-engine.ts:135-141`), so `max_per_day = 12` means twelve *trades* and one trade puts an NPC into a 2–6 hour cooldown at defaults, while out-of-window and starved picks fall back to the unrestricted picker with only a `console.warn` (`:6798-6808`, `:6831-6839`). The intelligence runner (`npc-intelligence-runner.ts:219-240`) and the reactive burst path (`npc-worker.command.listener.ts:648-693`) pick uniformly at random, and defense trades only stamp the last-participated marker (`:14957`), so with the 20 active NPCs in the workbench all enter cooldown within the first minute and the limits then shape nothing. The strategy radio adds nothing either: candidates carry `lastParticipatedAtMs: null` (`:6823`) so the LRU comparator ties and randomises (`npc-rotation.ts:301-317`), and `round_robin` uses a process-local cursor while the Redis cursor helper (`npc-rotation.redis.ts:305-318`) is never called.

**[Confirmed · High] Saving any NPC Behavior pace forces force-win ON and overrides `npc_force_win_enable`.** `admin.service.ts:3026-3039` always upserts `npc_behavior_preset` (storing `''` for "normal"), and on the next refresh `applyNpcPaceOutcomeStrategy` runs whenever that row exists (`:16262-16265`), unconditionally setting `this.forceNpcWinEnable = true` (`:16285`) — after `refreshConfig` has already read the operator's explicit `npc_force_win_enable` (`:16623-16624`). Once the tab has been saved once, even with "Normal", that switch is ignored forever, and force-win injects NPC volume to flip pots at the close.

**[Confirmed · Medium] Legacy mode runs three independent producers with different rule sets, and the admin copy describes only one.** `simulateTick` and its layers honour pace, aggression, asymmetry and (in the liquidity layer) rotation; the liquidity heartbeat (`:8848-9024`) honours only the undocumented `liquidity_*` keys; the intelligence runner and reactive bursts honour neither and size through `forceNpcTradeNoCap`. A comment at `:8603` puts the heartbeat at roughly 90 % of all legacy NPC trades and `npcAggressivenessMultiplier` is read only in the first producer, so the tape players see is dominated by the producers the settings do not govern.

**[Confirmed · Medium] In organic mode a rotation-ineligible arrival is dropped rather than re-picked.** `organic-npc-engine.ts:534-536` returns when the eligibility check fails, with no second pick, and `create-organic-engine.ts:125-134` checks only the Lua caps — so window, strategy and min-distinct are no-ops there and enabling rotation silently lowers the arrival rate below the configured momentum, while the tab's intro text (`NpcOrganicEngine.jsx:215`) says Rotation & Limits still apply.

**[Confirmed · Medium] NPC fills never reach the PWA as trades; only aggregates do.** `handleNpcTrade` (`redis.subscriber.ts:3136-3157`) deliberately emits no per-trade event, and the engine-side coalescer keeps only the last fill per battle per second (`npc-trade-publish.coalescer.ts:46-47`), so fills would be dropped even if an event existed. Players receive pots, the trader count (`battle-snapshot.publisher.ts:279-290`), chart price and volume, and leaderboard rows; adding a tape would require changing the coalescer contract.

**[Confirmed · Low, grouped] Smaller legacy NPC defects.** "Reset to defaults" sets pace to `calm` while the backend default is `normal` (`npcSimulator.jsx:46-49` against `admin.service.ts:2985-2987`), and the aggression input has no maximum while the engine clamps to [0.3, 3] (`:16254`). The NPC Traders tab renders a "recent trades" list from a field the status endpoint never returns (`:596`, `:1308-1321`). The A7b asymmetry plan is keyed by `stats.battleId` in one place and `this.currentBattleId` in two others (`:6556` against `:8641-8642`, `:8679-8680`), so two lead sides can apply in a round's first seconds. And the rotation window uses server-local `now.getHours()` (`npc-rotation.ts:180`) while the organic tab uses an explicit UTC offset, so on a UTC host "08:00–22:00" is UTC, not the operator's time.

### 2.8 Timer freezes and delayed updates under load (client point 5)

The engine heartbeat is not the problem: we measured `engine:events:timer` at a p90 gap of 1001 ms, and the value is deadline-derived rather than decremented, with missed seconds backfilled (`battle-engine.service.ts:767-772`, `:789-812`). Everything that freezes the countdown is downstream of it, or in the client.

**[Confirmed · High] The displayed countdown has no local clock.** `useBattleCountdown.js:30-43` renders `Math.floor(timer.time_remaining)` verbatim and documents that no local ticking is done; the helper that would derive it from an end time (`:23-27`) has no callers. There is no re-anchoring on reconnect either: `subscribeBattle` (`battle.gateway.ts:117-300`) emits a snapshot, balance, chat history, top traders and a dashboard but never a `timerUpdate`. Any hiccup therefore shows as a frozen number, and when frames resume the pacer drains at 250 ms and the number runs fast.

**[Confirmed · High] Every timer tick launches heavy database work on the single loop that also paces the timer.** The API is one PM2 fork instance carrying HTTP, Socket.IO and the Redis subscriber (`ecosystem.config.js:21-22`), and `forwardTimerNow` kicks `emitActiveTradeStreamUpdatesForBattle` on every forwarded tick (`redis.subscriber.ts:1366-1377`): five parallel reads (`trades.service.ts:4901-4928`) plus a projection cached on the *rounded price* for 300 ms (`:640-644`), recomputed on practically every tick, ending in an unbounded `priceTick.findMany` over the whole round (`battle-payout.live.ts:299-303`). The timer forward is itself a `setTimeout` (`:1182`) and inherits that latency, so it fires late, wire gaps exceed a second, the pacer switches to 250 ms catch-up, and the client shows freeze-then-jump.

**[Confirmed · High] Two engine publishers do unbounded work on the same tick as the heartbeat.** `RiskTerminalTickPublisher.publish` runs every heartbeat (`battle-engine.service.ts:864-874`) and per second performs `LRANGE 0 -1` of the whole stakes buffer and of the whole NPC-trade buffer, `priceTick.findMany` of all ticks of the round, two `battle.findUnique` and `rpcUser.findMany` of all rows, then projects over all of it (`risk-terminal-tick.publisher.ts:82-84`, `round-context.ts:161-185`); we saw both `LRANGE`s once per second in `MONITOR` and measured the publish at ~1085 B/s. `BattleSnapshotPublisher` separately reads both full leaderboard ZSETs with `ZRANGE 0 -1` and uses only `userIds.length` (`battle-snapshot.publisher.ts:282-288`), up to five times a second. Both costs grow linearly with trades and traders, on the loop that must fire the heartbeat.

**[Hypothesis · Medium] A leader-lease loss can black out every timer, price and snapshot forward for up to about 13 seconds.** The WS broadcaster lease has a 10 s TTL renewed every 3 s (`ws-broadcaster-leader.service.ts:17-23`), one failed renew sets `isLeader = false` (`:146-165`), and while not leader the subscriber discards engine-channel messages without parsing them (`redis.subscriber.ts:543-549`, default on). If the loop stalls past the TTL — which the findings above make plausible — everything is dropped until re-acquisition, with no client-side fallback; production logs containing `WS broadcaster leader lost` would settle it.

**[Confirmed · Medium, grouped] Further relay delays, client amplification and two guards that drop ticks.** `flushPendingTimerQueueOnBattleEnd` is awaited *before* `battleEnd` is emitted and sleeps one gap per queued tick (`redis.subscriber.ts:1245-1280`, emit at `:1509`), so a three-deep queue delays `battleEnd` by about three seconds, and timer frames go only to `battle_{id}`, so a socket still inside the subscribe pipeline of 2.11 misses them. On the client the watchdog forces a reconnect after about 10–12 s of silence with only 0–1 s of jitter (`useWebSocket.js:1399-1424`), and each reconnect re-runs the full subscribe bootstrap on the already-saturated process. While `battleIdRef.current` is null — between cooldown end and the first snapshot of the new round — every tick is rejected because each carries a battle id (`realtimeEventGuards.js:44-50`, `useWebSocket.js:921-922`), so the digits sit at `00:00` for the first second(s) of a round. **[Hypothesis · Low]** And the API stamps its synthesised `battle.started` tick with the API host's clock (`redis.subscriber.ts:2655-2667`) while engine ticks carry the engine host's, so the client's monotonic guard (`realtimeEventGuards.js:19-28`) would reject engine ticks for as long as the API clock leads — relevant only to multi-host production.

### 2.9 Money-path defects found on the way (must-fix before load)

These were not among the reported symptoms. We found them while tracing the hot paths, and they are why we would not put this build under load before fixing them.

**[Confirmed · Critical] The balance flush loses concurrent debits.** `user-balance-flush.service.ts:100-130` does `HGETALL`, then `prisma.user.update({ balance: { decrement } })`, then `DEL` — three operations with no atomicity — while the producer runs in another process and calls `HINCRBYFLOAT` (`user-spendable-balance.service.ts:139-146`). Any increment landing between the `HGETALL` and the `DEL` (a window as wide as the Postgres update latency, with users flushed sequentially every 500 ms) is deleted without being applied, and the dirty-user set has the same `SMEMBERS`-then-`DEL` pattern (`:80-90`). This is the default path in lean mode (`trades.service.ts:2424-2435`): the user keeps a balance they already staked.

**[Confirmed · Critical] A rolled-back trade leaves the user permanently short.** `queuePendingDebit` runs inside the Prisma transaction (`trades.service.ts:2429-2433`) and any later throw reaches the catch at `:2676-2682`, which writes a negative `HINCRBYFLOAT` (`user-spendable-balance.service.ts:165-169`) — but the flush clamps negatives away with `Math.max(0, …)` and deletes the key as nothing to do (`user-balance-flush.service.ts:103-114`). If the 500 ms flush runs between the debit and the rollback — which a transaction timeout, a Redis error or a failed `stakeBuffer.append` (`:2660`) will all produce — Postgres has been decremented, the credit is discarded, and no stake row exists.

**[Confirmed · Critical] Concurrent trade handling loses price updates in the engine.** `redis.subscriber.ts:93-97` registers one async handler per message with nothing serializing them, and `applyTradeExecuted` reads state (`market-state.service.ts:143`), awaits config (`:151`), computes from `state.lastPrice` (`:177`) and writes back at `:214`. ioredis delivers messages in one synchronous loop, so handler B reads the same pre-A state and overwrites A's write, losing A's price impact, pot totals and last-processed event id — with up to 48 concurrent trade publishes (`trade-command.env.ts:23`) plus the NPC worker on the same channel. This is money-affecting: `ticktrade:price:last` (the settlement final price) and `roundHigh`/`roundLow` derive from it.

**[Hypothesis · High] A crash between the debit and the stake write takes the money and loses the order.** The debit is queued at `trades.service.ts:2429` inside the transaction, while the durable record of the stake in lean mode is the Redis buffer append at `:2659-2673`, after it. A process exit in between — and 2.10 shows unhandled rejections kill both processes — leaves a debit the flush duly applies with no stake, and the idempotency key stays `pending` and goes stale after 60 s, so a retry places a second fully-charged order.

**[Confirmed · High] The trade coalescer discards idempotency keys when merging clicks.** `trade-order-coalescer.ts:115-119` sums amounts and collects keys, and `:212-213` forwards a key only when exactly one was collected, logging `idempotencyDiscarded` otherwise, while the claim happens downstream in `executeOrder` (`trades.service.ts:1197-1201`), after the merge. A client retrying the same key inside the 100–450 ms window has both submissions summed into one stake with no key, so neither the Redis claim nor `idempotency_records` can dedupe it. Gated by `TRADE_COALESCE_ENABLED` (default off), but the HTTP path always routes through the coalescer (`:3894`).

**[Hypothesis · High] The BullMQ worker skips the idempotency claim and its job lock is shorter than the transaction it runs.** The claim is explicitly skipped on the worker path (`trades.service.ts:1197`, `!execOpts?.worker`) while the transaction limits allow `maxWait` 15 s and `timeout` 35–120 s (`:2599-2602`) against BullMQ's 30 s default lock. A job exceeding the lock is redelivered, and the second run either times out on the 2 s spin lock and overwrites the result with `failed` — telling the user the trade failed while the first run succeeds — or executes the trade again with no guard.

**[Confirmed · Medium] Trades executed in the worker emit nothing to the user.** Queued trades run in `engine-worker`, an application context with no Socket.IO server, yet `TradesService` injects `WebsocketGateway` directly (`trades.service.ts:572`) and calls it for `balanceUpdated` (`:2974`), `equityUpdated` (`:2984`) and `notification` (`:3080-3081`) where `hasServer()` is false (`ws.gateway.ts:40-43`), so every emit returns early — and lean mode forces all real-user trades through that queue.

### 2.10 Engine stability defects (rounds that never start, dead engines)

**[Confirmed · Critical] `finishBattle` stops the timer before doing fallible I/O, so one failure leaves the engine idle forever.** `this.stop()` — clearing the heartbeat and the active-battle cache — runs at `battle-engine.service.ts:1085`, before the `battle.update` at `:1095-1098`, the `battle.end` publish at `:1109` and the settlement enqueue at `:1122`, and the only error handling logs (`:918-928`). Under database contention (a P2024 timeout on a pool shared with the per-second candle upsert and the risk-terminal queries) or a Redis blip the timer is already gone when the throw happens: no `battle.end`, no settlement job, no next battle, and the row stays ACTIVE/FINALIZE so nothing revisits it until the process restarts.

**[Confirmed · Critical] A failed settlement job can never be re-enqueued, and the next round depends on it.** The sole trigger for `createNewBattle` after a finish is the `settlement.completed` listener (`battle-engine.service.ts:1227-1242`, `settlement-completed.listener.ts:31-45`), plain at-most-once pub/sub. The job uses `jobId: battle-${battleId}` with `removeOnFail: { age: 86_400 }` (`settlement-queue.producer.ts:47-48`, `:61-63`) and BullMQ ignores an `add` while a job hash with that id exists, so the recovery service's re-enqueue with the same id (`battle-state-recovery.service.ts:97-100`) is a silent no-op for 24 hours. If settlement fails its three attempts (transaction timeout 30 s, `battle-settlement.service.ts:125-131`), the game stops and restarting the engine does not help. Even when it succeeds the next round is serialized behind it — the finish path first awaits the NPC align-at-close poll (up to 2 s, `index.ts:310-322`), and the 30.5 s cooldown starts only from `settlement.completed`.

**[Confirmed · High] Leader election drops leadership on any Redis error, and the restart overwrites live market state with stale database values.** A failed renew EVAL sets `isLeader = false` immediately (`engine-leader.service.ts:176-183`), stopping and 3 s later restarting the leader runtime, and `startEngine` then unconditionally rebuilds market state (`:661-677`) from `battles.buyPot`/`sellPot` — 0 mid-round because that row is written only at settlement (we confirmed battle 83 showing 0.00/0.00 while the Redis pot hash held the live totals) — resetting `roundHigh`/`roundLow` and `version` and publishing a synthetic price tick at `:653`. One Redis timeout therefore costs a 3 s timer gap, resets the pots the risk terminal reads, and clobbers the high/low that `finishBattle` later writes for settlement.

**[Confirmed · High] Both long-running processes die on an unhandled promise rejection and neither registers a handler.** We grepped `apps/engine/src`, `apps/api/src` and `packages/*/src` for `unhandledRejection`/`uncaughtException`: none, on Node 22, which terminates by default. The engine publishes its timer fire-and-forget with no `.catch` (`battle-engine.service.ts:798`, `:831`) on a shared connection with `maxRetriesPerRequest: 5`, so a brief Redis outage kills it and PM2 restarts it up to ten times, each restart re-running recovery and overwriting market state as above. On the API the equivalent call sites are `redis.subscriber.ts:706`, `:716`, `:737`, `:852`, `:1373` and `trades.service.ts:4875-4882` — including the per-second trade-stream refresh whose queries reject with P2024 under pool pressure — so the first escaping pool timeout takes the API down and triggers the reconnect storm of 2.8.

**[Confirmed · High] The timer shares one Redis connection with every bulk read.** `getSharedCommandRedis()` (`redis.client.ts:84-93`) returns a single instance used by the publisher, state service, market-state repository, candle store, pot cache and leaderboard reads, so the heartbeat's `PUBLISH` is written behind pending `LRANGE`/`ZRANGE` commands — the clean 1 Hz cadence we measured at idle is not representative of a loaded round.

**[Confirmed · Medium, grouped] Three further engine costs.** The price-tick coalescer drops the last tick of a burst instead of deferring it (`price-tick-coalesce.ts:12-19`) and the heartbeat never re-publishes a price although a `'heartbeat'` source exists (`battle-events.publisher.ts:4`), so the chart holds a stale price until the next trade. The candle bucket timer writes to Postgres every second with no re-entrancy guard (`index.ts:411-427`, `candle-store.service.ts:44`) — 300 rows per round holding a pool connection settlement also needs; we saw `[engine][slow_query] ms=358 … INSERT INTO "public"."candles" … ON CONFLICT` with no load. **[Hypothesis · Medium]** And the equity fan-out, if production overrides its default-off flags (`engine-hot-path.env.ts:20-30`), maps every user through an uncapped `Promise.allSettled` with two to three queries and a full buffer `LRANGE` each (`equity-pnl.publisher.ts:129-137`).

### 2.11 API and socket fan-out cost

**[Confirmed · High] Each client connect costs roughly 50 Prisma queries, and clients connect in waves.** Connection alone fires `emitCooldownStatusOnConnect` and `emitBootstrapBattleSnapshotOnConnect` (`ws.gateway.ts:272-273`, `:315-346`), then `subscribeToBattle` (`battle.gateway.ts:117-313`) runs `getActiveBattleId`, `battle.findUnique`, the bootstrap snapshot again, a Redis publish, `user.findUnique`, `getEquityAndPnlForBalanceEvent` (five queries), `getBattleChatMessages` with a 100-row limit and a COUNT, `getTopTradersForBattle`, `emitTradingDashboardUpdate` **twice** (`:298` and `:312`) and `getActiveTradesStream`, while the dedupe at `:192-229` skips only the bootstrap snapshot. The client doubles it (`emitSubscribeToBattle` sends the event twice per call, `useWebSocket.js:265-270`), and in the parity capture the phone performed the whole sequence **twice within 350 ms** — repeated by every client on each `newBattleStarted` and each reconnect wave, against a 30-connection pool.

**[Confirmed · High] `battleSnapshot` fan-out is per socket, with per-user async work, up to 12.5 times a second.** `emitPersonalizedToBattleRoom` (`ws.gateway.ts:410-437`) calls `fetchSockets()` (itself a Redis round-trip), awaits a three-await personalization per distinct user (`battle.service.ts:1353-1383`) and emits per socket, so the payload is encoded once per socket, while the coalescer tightens from 250 ms to 120 ms and then 80 ms in a round's last 25 s (`redis.subscriber.ts:2429-2438`). Each flush also forces a top-traders query that bypasses its own throttle (`battle.service.ts:2986-2994`) and triggers per-participant dashboards every 500 ms through an uncapped `Promise.allSettled` (`:2039-2043`). The 1 Hz timer frames queue behind all of it in the same per-socket write buffers.

**[Confirmed · Medium, grouped] Four avoidable costs on the same loop.** The Socket.IO Redis adapter is pure overhead at `instances: 1` — every emit is msgpack-encoded, published to Redis and received back for decoding before the self-check discards it, on the same shared connection the trade hot path uses (`redis-io.adapter.ts:29`, `redis.client.ts:93-102`). The `candleBatch` payload, identical for all viewers, is rebuilt per socket and twice per connect (`line-chart.gateway.ts:252-268`, `:530-570`), each build running up to a `priceTick.findMany` with `take: 10000` (`:651-656`). The active-trade-stream maps are keyed by `userId` for in-flight but `${userId}:${battleId}` for pending (`battle.gateway.ts:27-28`, `:355-362`), so a fast battle switch leaves an entry that is never read or cleared and the stream's first paint never arrives. And `chatHistory` has no rate limit and no role check while honouring `data.broadcast_to_all` with `this.server.emit(...)` (`:571-605`), so one client message becomes N × 100 rows of fan-out.

**[Confirmed · Low, grouped] Dead sockets and unguarded handlers.** Half-open sockets stay in rooms for about 110 s (`pingInterval` 20 s, `pingTimeout` `max(pingInterval + 10s, 90000)`, `redis-io.adapter.ts:36-55`), receiving every broadcast into a buffer. The WS auth guard performs three Redis reads per inbound message (`ws-auth.guard.ts:28-48`) and the rate limiter two sequential round-trips (`ws-rate-limit.service.ts:57-61`), while `subscribeToBattle`, `chatHistory` and `refreshAuth` are not rate-limited at all — the cheap handlers are protected and the expensive ones are open.

### 2.12 PWA shell performance

**[Confirmed · High] Foreground and resume trigger two independent forced syncs, each fanning out four subscribes.** Both `useWebSocket.js:403-429` and `ResumeSyncBridge.jsx:57-65` (via `useAppLifecycle`) listen for `visibilitychange`/`pageshow`/`resume` and call `syncNow({ force: true })`, and the 500 ms dedupe inside `syncNow` (`:364-401`) is explicitly bypassed by `force`. Each call emits `subscribeToPrice`, two `subscribeToBattle` and a line-chart `subscribe`, and if the socket reconnected `onConnect` adds three more while the server emits a `candleBatch` on connection regardless. The phone's double bootstrap within 350 ms in the parity capture is this path; each run costs the ~50-query pipeline of 2.11 plus up to 200 candles.

**[Confirmed · High] The resume snapshot is serialized to `sessionStorage` on every price tick; the throttle written for it is never called.** `ResumeSyncBridge.jsx:81-95` selects a slice including `price` and `timer`, so it fires up to 20 times a second, and `schedulePersistFromMatchSlice` (`:97-128`, throttle 750 ms) has no callers — the subscriber at `:130-166` calls `saveSnapshot` directly. That snapshot persists 20 top traders with avatar URLs, top performers, up to 20 active trades, 50 candles and the final battle snapshot (`appResumeStore.js:77-129`), so every tick synchronously stringifies and writes tens of kilobytes on the main thread.

**[Confirmed · Medium, grouped] Two more hot-path costs and three always-on frame loops.** The chart re-reads and re-parses that same `sessionStorage` mirror on every tick flush (`NewChart.jsx:1371-1375` into `:1301`, `persistCandleClosedSession.js:6-18`) and rebuilds the whole series, while each `candleClosed` reads, splices, sorts and re-stringifies the mirror (`:30-61`). Three loops run for the whole round regardless of change: the chart loop (`NewChart.jsx:1154`, plus a three-gradient glow redraw at `:501-564`), the pool bar (`TradingPanel.jsx:756-781`) and the dropped-frame telemetry monitor started in production at `useWebSocket.js:455`, whose `stopDroppedFrameMonitor` has no callers.

**[Confirmed · Medium] The resume snapshot is replayed into live stores on boot and never cleared on logout.** `appResumeStore.js:124-127` rehydrates on store creation and `hydrateMatchFromResume.js:130-164` accepts anything under five minutes old, applying the stored price, balance/equity display, top traders, active trades and candles before any socket data arrives, while `clearSnapshot` (`:84`) has no callers and neither `authStore.logout` nor `clearStorageOnLoginRedirect` touches `sessionStorage`. A fresh sign-in — including a different user in the same tab — therefore paints the previous session's values until the socket overwrites them.

**[Confirmed · Low] Components that only need refs subscribe to the hottest stores.** `NewChart.jsx:598-616` selects `lastLiveSnapshot` and `timer`, re-rendering on every 500 ms snapshot and every tick, with effects at `:1501-1523` re-seating the cursor map every second; `PriceBadge.jsx:20-23` selects the last candle *object*, which is new on every flush.

### 2.13 Housekeeping (unbounded keys, dead code, misconfiguration)

**[Confirmed · Low] Per-battle Redis keys are never expired, and several API maps grow without bound.** `market:state:<id>` (`market-state.repository.ts:68`, `SET` with no `EX`), `active:candle:<id>:1000` (`candle-store.service.ts:36`) and `chart:history:completed:<id>` (`line-chart.gateway.ts:772-797`, no `expire` in the file) persist forever: we measured 96 keys and 2.76 MB after 84 battles on a fresh database, and at roughly 288 rounds a day the chart history alone adds about 12 MB a day. In the API, `lastStreamSignatureByUser` (`trades.service.ts:337`, with a comment at `:5095-5097` acknowledging it), `lastTradingDashboardSignatureByUserAndBattle` (`battle.service.ts:274`) and `coalescedUserEmitLastAt` (`ws.gateway.ts:61`) accumulate an entry per user, or per user per battle, for the process lifetime.

**[Confirmed · Medium] Dead client contracts make the system look like it does things it does not.** The reconnect handlers are registered on the socket (`useWebSocket.js:1353-1354`) but socket.io-client v4 emits `reconnect` and `reconnect_attempt` on the *manager*, so `onReconnect` and its bootstrap never run and resubscription works only because `onConnect` also fires. `marketSnapshot` has a listener and no emitter; `subscribeToPrice` is emitted from four places (`:324`, `:393`, `:684`, `:1280`) with no handler anywhere in `apps/api`, yet the sync and reconnect logic is written as though it re-arms the price stream; the delta branches are unreachable because no delta emitters exist; and `chartStreamService.register` is never imported, so `NewChart`'s tick branch never runs and every tick goes through a full store rebuild.

**[Confirmed · Low, grouped] Dead configuration, build misconfiguration and documentation drift.** `npc_volume_target_amount_nudge_max` is parsed, validated and persisted with zero references in the engine (`npc-volume-shape.ts:413-418`); the `liquidity_*` keys that drive most legacy NPC trades have no admin UI. Hashed immutable assets are served `NetworkFirst` with no `networkTimeoutSeconds` (`vite.config.js:51-75`) although `dist/_headers` marks `/assets/*` immutable, the arena route chunks are not precached (`:26-31`), and console stripping is nested under `build.esbuildOptions` (`:149-152`), which Vite does not read — 38 `console.*` calls remain. (For the record the service worker is *not* a stale-data source: both runtime rules require the app's own origin and the API/socket origin matches no rule.) Finally `docs/ARCHITECTURE-DATA-FLOW.md:13` states there is no `sessionStorage` persistence while three mechanisms write to it on the hot path, the chart's comments claim a seamless cursor handoff (`NewChart.jsx:781-786`) and that offsets are never measured per frame (`:334-337`), and the admin copy for rotation ("sessions"), aggression ("react faster") and organic mode ("Rotation & Limits still apply") describes behaviour the engine does not implement.
