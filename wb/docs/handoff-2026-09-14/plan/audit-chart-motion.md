## F1 [CONFIRMED/high] Expiry-line map uses a stale barSpacing (always the LWC default 6 px) — slope, lead and 'spacingChanged' are all wrong
SYMPTOM: (3) line still not smooth: 6 px/s sawtooth; line hugs the newest bar instead of riding one column ahead; (1)/(2) line follows whatever the newest bar does
EVIDENCE: NewChart.jsx:395-402 `const bs = chart.timeScale().options()?.barSpacing;` — LWC 5.1 `TimeScaleApi.options()` returns `{...clone(this._private__timeScale._internal_options())}` and `TimeScale._internal_options()` returns `this._private__options`; `_private__options.barSpacing` is only READ (dev.mjs:6138 `this._internal_setBarSpacing(this._private__options.barSpacing)` and the constructor) and never written by `_private__setBarSpacing`/setVisibleRange/pinch. The chart never passes `barSpacing` in createChart options (:846-892), so the value is the default `barSpacing: 6` (dev.mjs:11990). Actual live spacing after `applyDefaultChartZoom` is plotWidth/80 ≈ 3.9 px on a 390 px phone (or plotWidth/2 = ~156 px when the series collapses, see F2). Used at :416 (`seedExpiryMap`), :437 (`(progress + EXPIRY_LEAD_BARS) * map.barSpacing`) and :1113-1116 (`spacingChanged` can never fire).
MECH: x_line = xRef(newest bar) + plotOffset + 6·(1+progress). Because `shiftVisibleRangeOnNewBar:true` keeps `rightOffset` constant on append (dev.mjs:6981-6986: compensation only runs when `!needShiftVisibleRangeOnNewBar`), the newest bar's pixel is STATIONARY (x = W − (rightOffset+0.5)·bs − 1, dev.mjs indexToCoordinate). Each append re-anchors the map (:1356-1357 → :1117 reseat) so the line ramps right 6 px over 1 s then snaps back 6 px — the in-code claim at :781-786 ('handoff is seamless … outgoing map has advanced exactly one bar-width, which is precisely where the incoming map starts') is false under shift; it would only hold if the viewport did not follow. Additionally progress is measured from the bar's bucket start (:419 `tRefMs = refBarSec*1000`) against local `Date.now()` (:727-733): a `candleClosed` bar arrives ≥1 s after its bucket start so progress clamps to 1 immediately (:435) → no motion at all in quiet seconds; when ticks arrive the anchor is the current second → fractional ramp. Motion therefore depends on trade cadence, and any client/server clock skew ≥1 s saturates progress to 0 or 1 (no server-offset estimation although `server_time` is in every candle payload).
FIX: Read live spacing: keep a `barSpacingRef` updated from `timeScale().subscribeVisibleLogicalRangeChange` via `(range.to-range.from)/timeScale().width()` or simply use `timeScale().logicalToCoordinate(i+1) - logicalToCoordinate(i)` at reseat; drop `options().barSpacing`. Then decide the intended semantics: (a) if the cursor should be pinned one column ahead of the newest bar, stop ramping (progress is meaningless when the bar pixel is stationary) — position = xRef + bs, no per-frame write; (b) if it should be a real time cursor, compute x from time: x = logicalToCoordinate(lastIndex) + ((nowServerMs − lastBarStartMs)/1000)·bs with nowServerMs = Date.now() + serverOffset (estimate offset from `server_time`/`timestamp` in candleClosed/priceUpdate), and let the viewport keep the cursor on screen (see F5). In both cases keep rAF-driven transform writes only (already the case) and interpolate between server ticks rather than clamping at 1 bar.
