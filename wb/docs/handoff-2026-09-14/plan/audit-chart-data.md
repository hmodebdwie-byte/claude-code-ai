ARCH: Engine: every executed trade (real or NPC) goes through trade-executed.handler.ts → MarketStateService.applyTradeExecuted (price from imbalance; `volumeScale = resolveTradeVolumeNotional(payload)` = trade $ amount) → BattleEventsPublisher.priceTick publishes `engine:events:price.tick` {battleId, price, displayPrice, timestamp: Date.now() ms, volumeScale}, but only if `shouldPublishEnginePriceTick` (200 ms per-battle coalescer) allows it; skipped ticks are dropped outright. The engine also runs its own CandleProjectionService (Redis `active:candle:<id>:1000`, DB `candles`, CANDLE_CLOSED/ACTIVE channels) which nothing in the API consumes. API (apps/api/src/redis/redis.subscriber.ts): the broadcaster-leader worker receives price.tick, dedupes by `price:${battle}:${ms}:${price}:${source}`, feeds LineChartGateway.handlePriceTick (aggregates 1-second OHLC + summed `volumeScale` into in-memory `liveCandles` for keys `battle_<id>` and `all`, persists closed candles to Redis zsets `chart:history:battle_<id>` (trimmed to MAX_POINTS=200) and list `ticktrade:candle:history`), and separately coalesces `priceUpdate` (200 ms) to the main socket room `battle_<id>` with `timestamp: floor(ms/1000)` seconds and `price = displayPrice`. A 1 Hz boundary timer closes candles (flat candles when idle) and publishes `candleClosed` (timestamp = bucket start in seconds, battle_id) over Redis `chart:events:closed` → every API worker forwards to its `/line-chart` room (`line_chart_all` for the client's default scope 'all'). On subscribe/connect and on each `battle.started`, `buildCandleBatchPayload` emits `candleBatch` containing ONLY the last 3 COMPLETED battles (archive zset `chart:history:completed:<id>`, else DB rebuild from `price_ticks` with volume = tick count), deduped by timestamp and sliced to 200 total points; the active battle's closed candles are never sent. Client (utils/useWebSocket.js): main socket `priceUpdate` → 40 ms throttle → RAF flush → lineChartStore.upsertLatestCandle (tick candle for the current second, volume 0); `/line-chart` `candleBatch` → appendCandleBatch + markServerHistoryReady; `candleClosed` → appendCandleBatch (dedupe key `ms:battle_id`, so the closed candle replaces the tick candle) + sessionStorage `tt_linechart_candleClosed_session_v1`; battle transitions call resetLineChart + unsubscribe/resubscribe (60–100 ms gap). NewChart.jsx merges store prices with the per-tab sessionStorage candles (`mergePricesWithSessionClosed`), slices to 200 points, builds an AreaSeries (close) + overlay HistogramSeries (server `volume`), does setData on first load / regressions and series.update for appends, and a RAF loop eases the last bar's value toward the latest tick (`series.update({time: lastTimeRef, value: display})`). Timestamps are UTC epoch seconds end to end; no local-time bucketing; the client never derives OHLC/volume itself; the PWA service worker (vite.config.js) caches only static assets (NetworkOnly for navigations; no API/socket caching).

## F1 [CONFIRMED/high] candleBatch never includes the ACTIVE battle; clients bootstrap with hours-old completed battles and then jump to the live price
SYMPTOM: (1) sudden spike line right after signing in / reconnecting on the phone; (2) charts differ per device
EVIDENCE: line-chart.gateway.ts:639-648 `getLastCompletedBattleIds(): … where: { status: 'COMPLETED' }, orderBy: { id: 'desc' }, take: HISTORY_BATTLE_LIMIT` and :820-836 `buildCandleBatchPayload … for (const bid of includedBattleIds) { const candles = await this.getClosedCandlesForBattle(bid, now) …}` — `activeBattleId` is looked up (:823-828) but only echoed as `active_battle_id`, never used to fetch candles. The active battle's closed candles DO exist: observed `chart:history:battle_80 ZCARD=192` while battle 80 was ACTIVE. Live DB at audit time: battle 80 ACTIVE started 13:52:28 UTC at ~1.2388; the three COMPLETED battles served (77,78,79) ended 01:07–01:18 UTC at 1.286–1.296. Client side: useWebSocket.js:565-583 `onCandleBatch … appendCandleBatch(normalizedCandles)`; NewChart.jsx:1498 effect deps `[api, activeBattleId, serverHistoryReady, chartEngineReady]` re-run on serverHistoryReady → applyFullSeriesReset sets `displayValueRef.current = last.value` (:1273, the 12-hour-old close) → first `priceUpdate` sets pendingTarget to the live price and the RAF (:1077 `areaSeriesRef.current.update({ time: lastTimeRef.current, value: display })`) eases from the stale close to the live price; the area series then draws a single steep segment between the last stale candle and the first live bar (lightweight-charts renders consecutive points adjacently — no time gap).
MECH: On connect/reconnect the only history the client can get is completed battles (hours old, different price regime). The current round's already-closed seconds are never sent, so the series goes old-close → live-price in one bar: visually a vertical spike/drop, animated by the easing loop. The same happens after a phone backgrounds and the socket reconnects: live candles missed while backgrounded are not backfilled. Also `applyDefaultChartZoom` (NewChart.jsx:236-255) fits the price scale to the last 80 bars, which span both regimes, exaggerating the jump.
FIX: line-chart.gateway.ts buildCandleBatchPayload: include the active battle's closed candles (in-memory `historyByKey.get('battle_<active>')` / Redis `chart:history:battle_<active>`) and cap by a time window (e.g. last N seconds) rather than 'last 3 COMPLETED ids'; optionally also emit the in-progress candle from `liveCandles`. Client: on candleBatch always setData the server window and drop any local candles older than the batch's first timestamp; on reconnect request a backfill `since=lastTimeRef`.

## F2 [CONFIRMED/high] Chart content is per-device/per-tab: server window + whatever ticks this device saw + sessionStorage merges + per-device caps

EVIDENCE: NewChart.jsx:143-163 `mergePricesWithSessionClosed` merges `loadCandleClosedSessionForBattle(bid)` (sessionStorage `tt_linechart_candleClosed_session_v1`, persistCandleClosedSession.js:31-62) into the series; :1301 `candles = mergePricesWithSessionClosed(candles, activeBattleId)`; :29 `MAX_SERIES_POINTS = STABILITY.MAX_CHART_POINTS` (=200, core/constants.js:13) vs store cap `MAX_CANDLES: 300` (constants.js:12, lineChartStore.js:5). ## F3 [CONFIRMED/high] Engine 200 ms tick coalescer drops trades' volume (volumeScale) instead of accumulating it; API ms-level dedupe drops more
SYMPTOM: (3) $100k order raised the bar, a ~$10k order later produced the same/higher bar
EVIDENCE: price-tick-coalesce.ts:12-19 `shouldPublishEnginePriceTick(battleId) { … if (now - last < PRICE_TICK_COALESCE_MS) return false; …}` (200 ms). trade-executed.handler.ts:276 `const publishPriceTick = shouldPublishEnginePriceTick(v1.battleId);` :281-300 `if (publishPriceTick) { … await this.events.priceTick(v1.battleId, state.lastPrice, displayPrice, volumeScale, {...}) }` — when false, nothing is published and `volumeScale` (= trade $ amount, market-state.service.ts:196 `resolveTradeVolumeNotional(payload)` / :236 `volumeScale: tradeVolumeNotional`) is discarded. API side sums only what arrives: line-chart.gateway.ts:936 `const tickVolume = Math.max(0, payload.volumeScale ?? 0)`, candle-aggregation.ts:57 `state.volume += Math.max(0, volume)`. Additional drop: redis.subscriber.ts:815-818 `dedupeKey = price:${battleId}:${eventTime}:${price}:${source}; if (this.priceTickDedupeKeys.has(dedupeKey)) return;` (two trades in the same ms at the same rounded price → second one's volume lost). Comment at redis.subscriber.ts:205 says engine publishes ~50 snapshots/sec at NPC peak, i.e. ≥90% of ticks are coalesced under load. Observed check in this quiet env (battle 80, 200-bar window): API zset sum 67,520 == engine per-trade `candles` sum 67,520 — no loss when trades are >200 ms apart, so the loss only manifests under bursty/NPC load.
MECH: Volume per candle is the sum of `volumeScale` of PUBLISHED ticks. A real $100k order that lands within 200 ms of a preceding tick (very likely during NPC bursts) is never published, so its notional never reaches the candle; a later $10k order that happens to be the first tick in its window is counted. Bars therefore reflect sampling luck, not traded notional.
FIX: In trade-executed.handler.ts keep a per-battle `pendingVolume` accumulator: add `volumeScale` when the coalescer returns false and flush the accumulated sum on the next published tick (or publish a tick when a real-user trade occurs regardless of the coalescer). Alternative: aggregate candle volume in the API from `trade.priced.v1` (TRADE_PRICED_CHANNEL, never coalesced, already carries `amount`) instead of `price.tick.volumeScale`. Make the API dedupe key include eventId, not (ms, price).

## F6 [CONFIRMED/medium] RAF easing writes interpolated values into series bars; closed bars keep the last eased sample, not the server close (frame-rate/background dependent)
SYMPTOM: (2) same data renders differently across devices; small residual wiggles
EVIDENCE: NewChart.jsx:1077 `areaSeriesRef.current.update({ time: lastTimeRef.current, value: display });` runs every frame with `display += (target - display) * alphaDisplay` (DISPLAY_TAU_MS=88, dt clamped by MAX_FRAME_DELTA_MS=80). candleClosed handling (:1404-1470) only sets `pendingTargetRef.current = closePrice` (:1435/:1444/:1466) and advances `lastTimeRef`; the store path writes the server value once (:1344 `areaSeriesRef.current.update(p)`) but the RAF immediately overwrites the same bar with `display`. When the next bar starts, the previous bar is frozen at whatever `display` had reached. In background tabs/phones RAF is paused, so the last bar freezes at an unconverged value until a full setData.
MECH: Rendered bar values are animation samples that depend on frame timing and tick arrival timing on each device rather than server candle closes, so two devices with identical server data can still differ pixel-wise, and a device resumed from background shows a wrong last bar.
FIX: On candleClosed (and when advancing lastTimeRef) write `series.update({ time: closedTime, value: close })` for the closed bar before moving on; ease only the in-progress bar; on visibilitychange→visible re-setData from the store; optionally drop easing on mobile.
