## F1 [CONFIRMED/critical] Concurrent trade.executed handling loses price updates (lost-update race on market state)
SYMPTOM: Price/chart lags or 'jumps back' under bursts; settlement final price and roundHigh/Low can omit trades' impact; instability under RPC load
EVIDENCE: redis.subscriber.ts L93-97: `this.redis.on('message', async (channel, message) => { ... await this.battleEngine.recalcPriceFromTrade(payload); ... })` — one async handler per message, nothing serializes them. market-state.service.ts L143 `const state = await this.repo.get(payload.battleId);` … L151 `const freezeSeconds = await this.configCache.getFreezeSeconds();` … L177 compute from `state.lastPrice` … L214 `await this.repo.set(nextState);`. Producer side: apps/api/src/trades/trade-command.env.ts L23 `TRADE_QUEUE_CONCURRENCY || '48'` — up to 48 trades published concurrently; npc-worker also publishes on the same channel.
MECH: ioredis emits every 'message' in one synchronous loop per socket read. Handler A yields at its first await; handler B starts and reads the SAME cached state (A has not called repo.set yet). Both compute price/pressure/version from the pre-A state; B's repo.set overwrites A's. A's price impact, pot totals, lastSequence and lastProcessedEventId are lost. Money-affecting because ticktrade:price:last (settlement final price) and roundHigh/roundLow derive from this path.
FIX: Serialize per battle: in RedisCommandSubscriber (or TradeExecutedHandler) push payloads onto a per-battle promise chain / async queue and process strictly FIFO (one in flight). Keep the queue bounded and drop only publishes, never state updates. Alternatively make applyTradeExecuted synchronous between get and set (read freezeSeconds from a sync cache, do repo.set's cache write before any await — the Redis SET can stay async).

## F2 [CONFIRMED/critical] finishBattle stops the timer before doing fallible I/O; any failure leaves the engine permanently idle with no round
SYMPTOM: Timer freezes at 0/1 s and never recovers until the process is restarted
EVIDENCE: battle-engine.service.ts L1085 `this.stop();` (clears setInterval, nulls activeBattleCache) executes BEFORE L1095-1098 `await this.prisma.battle.update({ where: { id: battleId }, data: updateData })`, L1109 `await this.events.battleEnd(...)`, L1122 `await this.settlementQueue.enqueue(...)`. The only error handling is L918-928 in publishTimerHeartbeat: `.catch((err) => { console.error(`[BattleEngine] runFinalizeAndSettlementCheck failed ...`) })`. `finally` at L1153-1156 just clears finishingBattles. No retry, no watchdog; the battle row stays ACTIVE/FINALIZE so nothing in-process ever revisits it.
MECH: Under DB contention (P2024 pool timeout — the pool is shared with the per-second candle upsert and risk-terminal queries) or a Redis blip (enqueue on a maxRetriesPerRequest:null connection can also hang forever), finishBattle throws after the timer is already cleared. No battle.end, no settlement job, no settlement.completed, no next battle. Only a process restart (BattleStateRecoveryService) heals it.
FIX: Do not call stop() until battle.end and the enqueue have succeeded (or move stop() after enqueue and keep the heartbeat idempotent while state==='CLOSE'). Wrap finishBattle in a bounded retry with backoff; on final failure publish battle.end anyway and schedule a recovery attempt (setTimeout) instead of dropping to idle. Add an in-process watchdog: if activeBattleId is null and no createNewBattle timer is pending for > cooldown+N s, run recoverBeforeEngineStart + start().

## F6 [CONFIRMED/high] Timer publish shares one Redis connection with all heavy traffic and any publish rejection crashes the process (no unhandledRejection handler)
SYMPTOM: Timer ticks arrive late/bunched under load; engine dies (PM2 restart storm, max_restarts 10) during Redis blips
