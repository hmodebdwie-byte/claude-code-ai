## F1 [CONFIRMED/high] candleBatch never contains the ACTIVE battle; the missing history collapses into a one-bar vertical jump (the 'spike') on sign-in and on every phone resume, and makes phone vs web charts differ
SYMPTOM: Spikes on the chart right after signing in from a phone; phone and web charts differ
EVIDENCE: Backend /home/claude/wb/backend/apps/api/src/ws/line-chart.gateway.ts:639-648 `getLastCompletedBattleIds(): where: { status: 'COMPLETED' } ... take: HISTORY_BATTLE_LIMIT` and 820-836 `buildCandleBatchPayload(...) { const includedBattleIds = await this.getLastCompletedBattleIds(); ... for (const bid of includedBattleIds) { const candles = await this.getClosedCandlesForBattle(bid, now); ...` — the active battle id is fetched (823-828) but only echoed as `active_battle_id`, never included. 881-899 `dedupeUnifiedCandlesByTimestamp ... return deduped.slice(-MAX_POINTS)` (MAX_POINTS=200, candle-types.ts:7). Observed live (node socket.io client against 127.0.0.1:18773/line-chart while battle 87 ACTIVE): `candleBatch active_battle_id=87 included=[84,85,86] candles=200 per-battle counts {'86':200}` — zero candles for 87. Redis has the active battle's history (`chart:history:battle_87`, 18 rows) but it is never sent. Client has no backfill path: /home/claude/wb/frontend/src/utils/useWebSocket.js:1591-1611 `requestLineChartBackfill` requires `lineChartBattleCursorRef.current` which the server always sets to `battle_cursor: null` (gateway 871). NewChart feeds lightweight-charts plain {time,value} points (NewChart.jsx:189-225 buildSeriesData) with no whitespace points, and lightweight-charts positions bars by index, so a 2-minute hole between battle 86's last candle and the first live tick of 87 is drawn as ONE bar step. MECH: Server history excludes the active round and the client never requests/receives it; the chart draws index-spaced bars so a time gap becomes a one-bar vertical jump.
FIX: Backend line-chart.gateway.ts buildCandleBatchPayload: append `getClosedCandlesForBattle(activeBattleId)` (reads chart:history:battle_<id>) plus the in-progress candle from liveCandles, and make the per-battle cap apply after including the active battle (or serve the active battle in its own `subscribe {battleId}` response instead of returning early on scope==='all' at 553-556).
