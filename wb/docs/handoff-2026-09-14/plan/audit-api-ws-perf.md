## F1 [CONFIRMED/critical] Balance flush loses concurrent debits: HGETALL → user.update → DEL is not atomic
SYMPTOM: Users retain balance they already staked (house loses money); spendable cache re-seeds from an un-debited Postgres balance after TTL
EVIDENCE: /home/claude/wb/backend/apps/api/src/trades/user-balance-flush.service.ts:100-130:
`const raw = await redis.hgetall(key); ... await this.prisma.user.update({ ... balance: { decrement: balanceDec } }); await redis.del(key);`
Producer runs in another process (engine-worker BullMQ job) at /home/claude/wb/backend/apps/api/src/trades/user-spendable-balance.service.ts:139-146: `await redis.hincrbyfloat(pk, 'balanceDec', fromBalance); ... await redis.sadd(DIRTY_USERS_KEY, ...)`. Flush is the default path: trade-hot-path.env.ts:156-164 `redisBalanceAuthorityEnabled()` returns true when `liveBattleRedisOnlyEnabled()` (default true, packages/shared/src/redis/live-battle-redis-only.ts:11-23) and trades.service.ts:2424-2435 skips `tx.user.update` in that mode.
MECH: Any HINCRBYFLOAT that lands between the flush's HGETALL and its DEL (window = Postgres UPDATE latency, seconds under load; flush loops users sequentially every 500 ms) is deleted without ever being applied to Postgres. Also flushAllDirty (lines 80-90) does SMEMBERS then DEL of the dirty set, so an SADD in between is dropped until the user trades again.
FIX: Make the drain atomic: Lua script that HGETALL+DEL (or RENAME pending → pending:flushing:<uuid>) and returns the values; apply to Postgres; on failure HINCRBYFLOAT the amounts back. Alternatively after a successful update do `HINCRBYFLOAT key balanceDec -balanceDec` instead of DEL and delete only when both fields are 0. Same for the dirty set: use SPOP-based draining, not SMEMBERS+DEL. Files: trades/user-balance-flush.service.ts.

## F2 [CONFIRMED/critical] rollbackPendingDebit credit is discarded by the flush's Math.max(0, …) clamp → user charged for a rolled-back trade
SYMPTOM: User balance debited in Postgres for a trade that failed/rolled back and never refunded
EVIDENCE: /home/claude/wb/backend/apps/api/src/trades/trades.service.ts:2429-2433 `queuePendingDebit` runs INSIDE the Prisma tx callback; on any later throw the catch at 2676-2682 calls `rollbackPendingDebit`, which does `redis.hincrbyfloat(pk, 'balanceDec', -fromBalance)` (user-spendable-balance.service.ts:165-169). The flush clamps: user-balance-flush.service.ts:103-114 `const balanceDec = Math.max(0, Number(raw.balanceDec ?? 0) || 0); ... if (balanceDec <= 0 && friendsDec <= 0) { await redis.del(key); continue; }`.
MECH: If the 500 ms leader flush runs between queuePendingDebit and rollbackPendingDebit (tx timeout/`getSpendable` Redis error/`stakeBuffer.append` failure at 2660 all land here), Postgres is decremented, the rollback writes a negative pending value, and the next flush deletes it as "nothing to do". The user is permanently short the stake amount with no stake row.
FIX: Never clamp: apply negative pending values as `balance: { increment }` (or a compensating ledger row). Better: move `queuePendingDebit` out of the tx and only queue after the durable stake write (`stakeBuffer.append` / `tx.stake.create`) has succeeded; keep the Redis reserve (`tryReserve`) as the only pre-commit hold. Files: trades/trades.service.ts (2424-2435, 2659-2674, 2676-2690), trades/user-balance-flush.service.ts.

## F3 [HYPOTHESIS/high] Pending debit + reserve persisted before the stake row: process crash between them loses the order but keeps the debit
SYMPTOM: After a worker restart under load, users report money taken with no position
EVIDENCE: /home/claude/wb/backend/apps/api/src/trades/trades.service.ts:2429 `await this.spendableBalance.queuePendingDebit(...)` (inside tx) vs 2659-2673 `await this.stakeBuffer.append({...})` (after tx, in lean default mode the only durable record of the stake, see 2497-2499 `stakeId = tempStakeId`). No compensation runs on process exit; `rollbackPendingDebit` only runs in the catch block.
MECH: With LIVE_BATTLE_REDIS_ONLY (default) the stake exists only in the Redis buffer list appended AFTER the debit is queued. A crash (see F6: unhandled rejections crash Node 22) or SIGKILL/PM2 max_memory_restart between 2429 and 2660 leaves a debit that F1's flush applies to Postgres with no stake. Idempotency key stays `pending` (stale after 60 s) so a client retry places a second, fully-charged order.
FIX: Write the stake buffer row and the pending debit in one Redis MULTI (or one Lua) so they are atomic; or append the stake first and queue the debit second with a reconciliation job that matches pending debits to buffered stakes. Files: trades/trades.service.ts.

## F4 [CONFIRMED/high] TradeOrderCoalescer drops idempotency keys when merging and double-counts a retried click
SYMPTOM: Duplicate/over-sized stake when a client retries a click (only if TRADE_COALESCE_ENABLED=true; default off)
EVIDENCE: /home/claude/wb/backend/apps/api/src/trades/trade-order-coalescer.ts:115-119 `st.sum += amount; ... if (idempotencyKey) st.idempotencyKeys.push(idempotencyKey);` and 212-213 `const idem = st.idempotencyKeys.length === 1 ? st.idempotencyKeys[0]! : null;` (logged as `idempotencyDiscarded`).
